# План реализации — Fintech Transaction Simulator

> Пошаговый план разработки от пустого репозитория до рабочего демо.
> Разбит на этапы так, чтобы после каждого этапа было что показать и на чём остановиться,
> если времени не хватит.

Общая оценка: **~25-35 часов** чистого времени при уверенном знании Java/Spring.
Реалистично — 2-3 недели по вечерам.

---

## Этап 0. Подготовка окружения (0.5-1 час)

**Цель:** поднять всю инфраструктуру одной командой, ничего ещё не кодируя.

- [x] Создать `docker-compose.yml` с сервисами:
  - `kafka` (образ `apache/kafka`, режим KRaft, без Zookeeper)
  - `redis` (образ `redis:7-alpine`)
  - `postgres` (образ `postgres:16-alpine`, с `POSTGRES_DB=fintech`)
- [x] Проверить, что `docker compose up -d` поднимает все три контейнера без ошибок.
- [x] Установить локально клиенты для проверки: `redis-cli`, `psql`, и любой Kafka UI
  (например, **Kafka UI** от provectus — добавить его же в docker-compose, это удобно
  для отладки и хорошо смотрится на демо).
- [x] Создать пустой репозиторий на GitHub, добавить `.gitignore` (Java + Node шаблоны).
- [x] Создать структуру папок проекта.
- [x] Создать `application.yml` с базовыми конфигурациями.

**Критерий готовности:** `docker compose ps` показывает контейнеры в статусе `healthy`.

## Этап 1. Скелет Spring Boot проекта (1-2 часа)

**Цель:** пустое приложение стартует и подключается ко всем трём хранилищам.

- [x] Сгенерировать проект через [start.spring.io](https://start.spring.io):
  Maven, Java 21, Spring Boot 3.3.x, зависимости: Web, Kafka, Data Redis, Data JPA,
  PostgreSQL Driver, Lombok, Validation, Actuator.
- [x] Настроить `application.yml` (YAML вместо properties).
- [x] Подключить **Flyway** для миграций БД.
- [x] Написать первый health-check тест: приложение стартует, `/actuator/health`
  отвечает `UP` по всем трём компонентам.

**Критерий готовности:** `./mvnw spring-boot:run` стартует без ошибок, health-check зелёный.

## Этап 2. Модель данных и миграции (1.5-2 часа)

**Цель:** таблицы в PostgreSQL, включая outbox.

- [x] Написать Flyway-миграцию `V1__init.sql`:
  - `accounts` (id, owner_name, balance, currency, created_at)
  - `transactions` (id, account_id, amount, status, idempotency_key, created_at, updated_at)
  - `outbox_events` (id, aggregate_id, event_type, payload jsonb, created_at, processed_at)
- [x] Создать JPA-сущности: `Account`, `Transaction`, `OutboxEvent`.
- [x] Создать репозитории (`AccountRepository`, `TransactionRepository`, `OutboxRepository`).
- [x] Написать сидер (через Flyway-миграцию `V2__seed_data.sql` с данными).

**Критерий готовности:** таблицы видны в `psql`, тестовые аккаунты заполнены.

---

## Этап 3. Producer + Transactional Outbox (2-3 часа)

**Цель:** REST-эндпоинт `POST /api/transfer`, который атомарно пишет транзакцию и outbox-событие.

- [x] Создать DTO: `TransferRequest` (fromAccountId, toAccountId, amount).
- [x] Создать `TransferController` с методом `POST /api/transfer`.
- [x] Создать `TransferService.createTransfer(...)` с `@Transactional`.
- [x] Написать `OutboxPublisher` — планировщик (`@Scheduled`), который публикует события в Kafka.
- [x] Настроить топик `transactions` (автоматически через KafkaAutoConfiguration).

**Критерий готовности:** curl-запрос на `/api/transfer` создаёт строку в БД и сообщение
видно в Kafka UI в топике `transactions`.

---

## Этап 4. Rate Limiting в Redis (1-1.5 часа)

**Цель:** защитить API от перегрузки одним пользователем.

- [x] Реализовать token bucket или простой fixed-window limiter на Redis:
  ```
  INCR rate:{accountId}:{minuteBucket}
  EXPIRE rate:{accountId}:{minuteBucket} 60   (выставлять только при первом INCR)
  ```
- [x] Добавить проверку в `TransferService` перед созданием транзакции —
  если лимит превышен, возвращать `429 Too Many Requests`.
- [x] Написать unit-тест на превышение лимита (можно с embedded Redis
  или Testcontainers).
- [x] Настроить Maven wrapper (`./mvnw`) для обеспечения консистентности сборки.

**Критерий готовности:** при 20+ запросах в минуту с одного счёта API начинает
отвечать 429.

---

## Этап 5. Consumer — обработка транзакций (3-4 часа, самый важный этап)

**Цель:** консьюмер читает Kafka, идемпотентно и безопасно обновляет баланс.

- [x] Создать `TransactionProcessorListener` (`@KafkaListener(topics = "transactions")`).
- [x] Реализовать идемпотентность:
  - Перед обработкой — `SET NX` в Redis по ключу `processed:{transactionId}` с TTL (например 24 часа).
  - Если ключ уже существует — сообщение пропускается (уже обработано), просто коммитим оффсет.
- [x] Реализовать distributed lock на аккаунт (через **Redisson**, метод `RLock.tryLock(...)`):
  - Лочим `lock:account:{accountId}` перед списанием/зачислением средств.
  - Лочим оба счёта в переводе — **в детерминированном порядке (например, по возрастанию ID)**,
    чтобы избежать deadlock между двумя параллельными переводами "туда-обратно".
- [x] Внутри лока:
  - Читаем баланс из Redis-кэша (или из БД, если кэш промахнулся — cache-aside).
  - Проверяем достаточность средств.
  - Обновляем баланс в БД (`UPDATE ... SET balance = balance - :amount`) и инвалидируем/обновляем кэш.
  - Обновляем статус транзакции на `COMPLETED` или `FAILED` (если средств не хватило).
- [x] Настроить `ConcurrentKafkaListenerContainerFactory` с ручным `ackMode = MANUAL`,
  чтобы коммитить оффсет только после успешной обработки (не автокоммит).

**Критерий готовности:** серия параллельных переводов между одними и теми же
счетами не приводит к неверному балансу (написать нагрузочный тест — отправить
50 переводов подряд и свериться с ожидаемой суммой).

---

## Этап 6. Retry + Dead Letter Queue (1.5-2 часа)

**Цель:** сообщения, которые не удалось обработать, не теряются и не блокируют очередь.

- [x] Настроить `DefaultErrorHandler` со `FixedBackOff` (например 3 попытки с интервалом 1с).
- [x] Настроить `DeadLetterPublishingRecoverer` — после исчерпания попыток сообщение
  публикуется в топик `transactions.DLT`.
- [x] Написать простой эндпоинт или лог-алерт для мониторинга DLQ (в реальном проекте
  сюда бы подключался Slack-алерт или дашборд).

**Критерий готовности:** искусственно сломанное сообщение (например, несуществующий
account_id) после 3 попыток оказывается в `transactions.DLT`, видно в Kafka UI.

---

## Этап 7. Детекция аномалий на основе правил и эвристик (2-3 часа)

**Цель:** отдельный консьюмер анализирует поток и находит подозрительные паттерны с помощью эвристик (без платных AI-API).

- [x] Создать `AnomalyDetectorListener` — отдельная consumer group (`fdb-anomaly-group`) на топик `transactions`.
- [x] Реализовать правила эвристического анализа:
  - Правило: более 5 переводов с одного счёта за 1 минуту (velocity check через Redis).
  - Правило: аномально большая сумма перевода (превышение порога 50,000).
- [x] При срабатывании правил сформировать `AnomalyAlert` и опубликовать в Redis Pub/Sub канал `alerts`.
- [x] Написать юнит-тесты на детекцию аномалий (`AnomalyDetectorListenerTest`).

**Критерий готовности:** подозрительные транзакции корректно детектируются правилами и публикуют алерты в Redis Pub/Sub, тесты зелёные.

---

## Этап 8. Симулятор нагрузки (1 час)

**Цель:** приложению есть чем "дышать" без участия реального пользователя.

- [ ] Написать `@Scheduled`-джобу или отдельный маленький CLI-скрипт, который раз
  в 1-3 секунды создаёт случайный перевод между двумя случайными тестовыми счетами.
- [ ] Добавить возможность включать/выключать симулятор через эндпоинт
  (`POST /api/simulator/start`, `/stop`) — удобно для демонстрации на собеседовании:
  "смотрите, включаю нагрузку — видно, как летят сообщения в Kafka UI".

**Критерий готовности:** можно запустить симулятор и наблюдать живой поток
транзакций в логах/Kafka UI/дашборде.

---

## Этап 9. Frontend — минимальный дашборд (3-4 часа)

**Цель:** 1-2 страницы, показывающие всю магию бэкенда наглядно.

- [ ] Страница 1 — **Dashboard**:
  - Список счетов с текущими балансами (обновление через WebSocket/SSE).
  - Кнопка "сделать перевод" (форма: from, to, amount) → вызывает `/api/transfer`.
  - Живая лента последних N транзакций со статусами.
- [ ] Страница 2 — **Alerts**:
  - Живая лента алертов об аномалиях, приходящих через WebSocket
    (backend транслирует из Redis Pub/Sub в WebSocket-сессии, например через
    `spring-boot-starter-websocket` + STOMP, либо просто SSE — проще в реализации).
- [ ] Простой график (Recharts) — количество транзакций в минуту, чтобы наглядно
  показать нагрузку от симулятора.

**Критерий готовности:** открываешь дашборд, включаешь симулятор — видно, как
меняются балансы и появляются транзакции в реальном времени без перезагрузки страницы.

## Этап 10. Наблюдаемость и тесты (2-3 часа, если останется время)

- [ ] Подключить **Micrometer + Prometheus** — экспортировать метрики: consumer lag,
  количество обработанных/упавших транзакций, латентность обработки.
- [ ] (Опционально) поднять **Grafana** в docker-compose с готовым дашбордом.
- [ ] Написать интеграционные тесты через **Testcontainers**:
  - Полный цикл: POST /transfer → outbox → Kafka → consumer → баланс обновлён.
  - Тест на конкурентность: параллельные переводы между одной парой счетов.
  - Тест на идемпотентность: повторная доставка одного и того же сообщения
    не должна задвоить списание.

**Критерий готовности:** `./mvnw test` зелёный, есть хотя бы 3-5 осмысленных
интеграционных теста, а не только unit-тесты на геттеры.

## Итоговая последовательность (кратко)

```
0. Docker Compose
1. Скелет Spring Boot
2. БД + миграции
3. Producer + Outbox
4. Rate Limiting (Redis)
5. Consumer + идемпотентность + distributed lock   ← ядро проекта
6. Retry + DLQ
7. Spring AI детекция аномалий
8. Симулятор нагрузки
9. Frontend-дашборд
10. Observability + тесты
11. Полировка и подготовка к демо
```

**Если времени критически мало** — этапы 0-6 дают полноценную историю для
собеседования даже без AI и без красивого фронтенда: outbox, идемпотентность,
distributed lock и DLQ уже закрывают 80% интересных вопросов.
